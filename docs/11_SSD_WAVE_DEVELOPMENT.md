# 11 — SSD 驱动开发与 Wave 机制

## 11.1 SSD 定义

本项目将 SSD 定义为：

```
Spec → Schema → Delivery
规格 → 数据/接口契约 → 可验收交付
```

如果团队成员习惯称为 SDD（Spec Driven Development，规格驱动开发），在本项目中与 SSD 的目标一致：先明确规格，再写 Schema 和 API 契约，最后按 Wave 交付。

## 11.2 SSD 三阶段

### S1：Spec 规格

每个能力开发前必须明确：

- 用户是谁
- 解决什么问题
- 页面或 API 行为是什么
- 成功和失败状态是什么
- 管理员是否可配置
- 是否影响移动端 API

### S2：Schema 契约

进入开发前必须明确：

- PostgreSQL 表结构
- Prisma Schema
- DTO 类型
- API 请求和响应
- 错误码
- 权限要求
- 审计日志字段

### S3：Delivery 交付

每个 Wave 必须包含：

- 开发任务
- 验收标准
- 测试范围
- 迁移脚本
- 回滚策略
- 文档更新

## 11.4 Wave 文档要求

每个 Wave 必须有：

```
docs/prompts/waveN_prompt.md
```

内容结构：

1. 必读文档
2. 技能辅助建议
3. 前置条件
4. 目标
5. 任务清单
6. 数据库变更
7. API 变更
8. 前端变更
9. 安全要求
10. 验收标准
11. 禁止事项

## 11.5 技能辅助开发规范

本项目鼓励在开发过程中主动使用相关 Codex Skills/Plugins 辅助，但使用技能前仍必须先阅读本项目文档和当前 Wave 提示词。

推荐使用场景：

| 场景 | 建议 |
|------|------|
| 需求和规格不清晰 | 使用文档协作、规格梳理、计划拆分相关技能辅助收敛范围 |
| 前端页面和交互实现 | 使用前端应用、UI/UX、浏览器测试相关技能辅助设计和验证 |
| 后端、数据库和 API | 使用系统化调试、数据库最佳实践、接口文档相关技能辅助实现 |
| OpenAI 兼容协议和模型接入 | 使用 OpenAI 官方文档查询相关技能确认最新 API 行为 |
| Bug、测试失败和线上问题 | 使用系统化调试技能先复现、定位、验证，再修改 |
| 完成前验证 | 使用验证和代码审查相关技能辅助检查遗漏、风险和测试覆盖 |
| GitHub/CI/PR 工作 | 使用 GitHub、CI 修复、PR 评论处理相关技能辅助协作 |

技能使用原则：

1. 技能是辅助，不替代 `docs/` 文档、AGENTS 规则和当前 Wave 验收标准。
2. 涉及安全、认证、CORS、密钥、数据库迁移和部署时，必须以当前升级文档为准。
3. 使用技能生成的方案必须落到明确文件、接口、测试和验收项中。
4. 发现技能建议与项目规范冲突时，优先遵守项目规范，并在实现说明中记录取舍。

## 11.7 Wave 完成标准

每个 Wave 结束前：

- TypeScript 无编译错误
- 后端单元测试和 e2e 测试通过
- 前端构建通过
- 数据库迁移可重复执行
- OpenAPI 文档更新
- 关键接口有成功和失败验收
- Vercel 前端可访问独立后端
- CORS 白名单在生产域名下验证通过
